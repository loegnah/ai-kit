# AI-Native SDLC 플레이북 (AI 네이티브 소프트웨어 개발 라이프사이클)

> 원문: [The AI-Native SDLC playbook | Claude by Anthropic](https://claude.com/blog/the-ai-native-sdlc-playbook) (Louis Claxton)

AI 코딩 에이전트(Claude Code 등)의 등장으로 구현(Build) 속도는 전례 없이 빨라졌으나, 전통적 승인 절차, 검토 회의, 핸드오프 방식은 그대로 유지되어 전체 생산성이 정체되고 있습니다.
본 플레이북은 소프트웨어 개발 수명 주기(SDLC) 6단계를 AI 네이티브 루프로 전면 재구성하는 실천 가이드입니다.

---

## 1. 패러다임 전환: 전통적 SDLC vs AI-Native SDLC

- **핵심 문제**: 코드는 더 이상 병목이 아닙니다. 구현(Build) 단계가 수 시간으로 단축되면서, 사람 속도로 동작하는 앞뒤 단계(기획, 검토/테스트, 배포)가 새로운 병목이 되었습니다.
- **핵심 해법**: 일방향 선형 프로세스를 **버전 관리 아티팩트 기반의 지속적 피드백 루프(Continuous Loop)**로 전환합니다.
  - 각 단계는 Git으로 추적되는 마크다운/코드 아티팩트를 커밋하며 다음 단계를 자동 트리거합니다.
  - `intent.md` → `spec.md` → `plan.md` → diff 및 테스트 → PR 검토 결과 → 인시던트/평가 기록으로 이어지는 커밋 체인이 곧 감사 추적(Audit Trail)이 됩니다.
  - 인간은 모든 줄을 수동 확인하는 대신, 각 관문(Gate)에서의 의도 판단과 위험 평가에 집중합니다.

### 6단계 비교표

| 단계                       | 전통적 SDLC                                   | AI-Native SDLC                                                                                   |
| :------------------------- | :-------------------------------------------- | :----------------------------------------------------------------------------------------------- |
| **1. Plan (기획)**         | 위원회 논의, 회의, 티켓 작성 등 긴 수기 절차  | 제안자가 Claude와 브레인스토밍 후 실행 가능한 `intent.md`로 즉시 작성                            |
| **2. Design (설계)**       | 분석가의 요구명세서 작성 후 디자이너가 재해석 | 에이전트와의 1회 세션으로 요구사항과 설계를 압축, 사내 정책 스킬(Skills)을 반영해 `spec.md` 도출 |
| **3. Build (구현)**        | 개발자의 단독 수기 코딩 및 사후 문서화        | 에이전트 Plan Mode 기반으로 계획 확정 후 구현, 사내 지식은 `CLAUDE.md`와 스킬로 자산화           |
| **4. Test (검증)**         | 단계 경계에서 수동 QA 검증                    | 구현 중 에이전트 자체 피드백 루프 및 CI 기반 에이전트 설정 지속 평가(Continuous Evals)           |
| **5. Deploy (배포)**       | 전수 수기 코드 리뷰 및 비정기 배포 심의       | 에이전트 양방향 PR 리뷰, 릴리스 관문 훅(Hooks), 샌드박스 CI/CD 자동화                            |
| **6. Maintain (유지보수)** | 장애 후 인간의 수동 접수 및 대응 대기         | 모니터링 에이전트가 지표 이탈 감지 시 원인 진단 후 `intent.md`를 발행하여 루프 재기동            |

---

## 2. 단계별 실행 플레이 (Plays)

```
[Plan: intent.md] ──> [Design: spec.md] ──> [Build: plan.md + 코드]
        ▲                                                  │
        │                                                  ▼
[Maintain: 모니터링/루프] <── [Deploy: PR/승인 관문] <── [Test: 피드백/Evals]
```

---

### Stage 1: Plan (기획) — `intent.md`로 의도 캡처

누군가 대신 작성해주기를 기다리지 않고, 제안자 자신의 언어로 즉시 버전 관리 가능한 아티팩트를 작성합니다.

- **배경**: 전통 방식에서는 아이디어가 백로그, 사용자 스토리, 산정 회의를 거치며 원래 의도가 왜곡됩니다. AI 네이티브 환경에서는 문제 정의, 목표, 제약조건을 담은 프로토타입 명세를 즉시 작성합니다.
- **실행 절차**:
  1. 제안자가 현재 겪는 문제, 원하는 개선 결과, 제외 범위를 Claude에게 자유롭게 설명합니다.
  2. Claude가 분석가처럼 사용자, 범위, 제약조건, 성공 기준을 질문하며 구체화합니다.
  3. 사내 템플릿 스킬에 맞춰 `intent.md` 파일로 작성합니다 (레포 내 `intent/` 디렉토리 관리 권장).
  4. 제안자가 검토/수정한 후 Git에 커밋합니다 (Git이 낯선 직원은 Cowork 또는 커넥터 도구 활용).
  5. 제품 책임자(PO)가 내용을 검토하고 승인(머지)하면 Design 단계가 시작됩니다.
- **아티팩트 예시 (`intent.md`)**:
  ```markdown
  # 의도: 보험금 청구 상태 셀프 서비스

  작성자: J. 오티즈 (보상운영팀) / 상태: 초안

  ## 문제 정의

  고객들이 청구 건의 진행 상황을 묻기 위해 고객센터로 계속 전화함.
  상담원이 단순 상태 안내 문의에 전체 통화 시간의 약 1/3을 소모함.

  ## 제안 결과

  고객이 직접 포털에서 청구 상태, 다음 처리 단계, 예상 완료일을 확인.

  ## 영향 받는 사용자와 시스템

  보상 담당자, 고객 포털 팀, 보상 핵심 API(claims-core).

  ## 제약조건

  포털 세션에 신규 개인정보(PII)를 추가 노출하지 않을 것. 기존 인증 체계만 사용.

  ## 미해결 질문

  외부 손해사정사도 해당 조회 권한이 필요한가?
  ```
- **측정 지표**:
  - **선행 지표**: 첫 논의부터 `intent.md` 커밋까지 걸린 시간 (수 주 단위에서 수 시간으로 단축).
  - **후행 지표**: PO의 승인 통과율(Survival rate), 첫 `spec.md` 생성 후 `intent.md`가 수정된 횟수.

### Stage 2: Design (설계) — 요구사항과 설계 압축

사후 리뷰 회의에서 정책 위반을 뒤늦게 발견하는 대신, 명세를 작성하는 시점에 보안, 브랜드, UX 표준을 즉시 적용합니다.

- **배경**: 전통적으로 분석가의 요구정의와 디자이너의 설계는 분리되어 느리고 정보 손실이 컸습니다. AI 네이티브 환경에서는 두 작업이 에이전트 세션 하나로 압축됩니다.
- **실행 절차**:
  1. PO가 사내 표준 스킬(보안, 규정 준수, 브랜드, UX)이 장착된 Claude 세션에 승인된 `intent.md`를 전달합니다.
  2. 프롬프트를 통해 코드베이스 연동 명세 작성 및 정책 충돌이나 우려되는 영역을 명시적으로 플래그하도록 지시합니다.
  3. 프론트엔드 작업의 경우 `Claude Design`을 통해 `intent.md` 기반으로 화면 목업을 생성하고 조율합니다.
  4. 에이전트가 플래그한 우려사항을 관련 정책 담당자와 협의하여 해결합니다.
  5. `spec.md`를 `intent.md`와 함께 커밋합니다. PO 및 테크 리드가 검토 후 승인하면 Build 단계로 진입합니다.
- **프롬프트 예시**:
  ```markdown
  첨부된 intent.md를 읽고 기존 코드베이스 연동을 위한 요구사항 및 설계 명세를 작성해줘.
  사용 가능한 사내 스킬을 적용하여 브랜드 가이드라인, 보안 정책, UX 표준을 준수하도록 해줘.
  엔지니어링 팀에 바로 인계할 수 있도록 spec.md 파일로 상세히 문서화해줘.
  상충되는 정책으로 인해 만족하기 어려운 지점이나 우려되는 영역이 있다면 명확하게 표시해줘.
  ```
- **측정 지표**:
  - **선행 지표**: `intent.md` 커밋부터 `spec.md` 커밋까지 걸린 시간.
  - **후행 지표**: 구현 착수(`plan.md` 커밋) 이후 `spec.md`가 변경된 횟수(요구사항 재작업 비율).

### Stage 3: Build (구현) — 계획 기반 구현 및 지식 자산화

#### Play 3-1: Claude Code Plan Mode 기본화

- **무작정 코드 작성 금지**: 엔지니어는 Claude Code를 **Plan Mode**로 실행하여 시작합니다.
- 승인된 `spec.md`를 입력하고, 변경할 파일 목록, 작업 순서, 증명할 테스트를 담은 구현 계획을 요구합니다.
- "이 변경으로 인해 깨질 수 있는 부분", "가장 위험한 단계", "선택하지 않은 대안"을 질문하며 계획을 다듬습니다.
- 제3자 엔지니어가 계획만 보고도 구현할 수 있을 수준이 되면 `plan.md`로 커밋합니다.
- 계획이 승인된 후 코드를 구현합니다. 계획과 다르게 진행되면 동일 커밋에서 `plan.md`도 업데이트합니다.
- **구현 계획 예시 (`plan.md`)**:
  ```markdown
  # 구현 계획: 청구 상태 셀프 서비스 (intent.md 기반)

  ## 변경 대상 파일

  - portal/src/claims/StatusPanel.tsx (신규 생성)
  - claims-api/routes/status.py
  - claims-api/tests/test_status.py

  ## 작업 순서

  1. 기존 인증 기반 하에 status 엔드포인트 추가.
  2. 해당 엔드포인트를 호출하는 StatusPanel 컴포넌트 개발.
  3. 포털 메인 네비게이션에 패널 연동.

  ## 위험 요소

  - claims-core API 호출 제한(50 rps): 패널 단 캐싱 필수 적용.

  ## 검증 방법

  - test_status.py: 청구 진행 4개 상태 테스트 케이스 통과.
  - 스크린샷 캡처: 승인된 디자인 목업과 대조 일치 확인.
  ```

#### Play 3-2: Auto Mode 및 병렬 세션 (Parallel Sessions & Subagents)

- 일상적이고 위험 범위가 좁으며 테스트가 갖춰진 작업은 계획 승인 후 건별 확인 없이 자율 실행하는 자동 모드(`auto mode`)를 적용합니다.
- **병렬 세션**: 작업 파일이 겹치지 않는 독립적인 작업은 Git worktree를 이용해 별도 터미널에서 병렬 실행합니다 (`claude --worktree 기능A`, `claude --worktree 기능B`).
- **서브에이전트**: 최종 검증, 코드 단순화, 코드베이스 탐색 등 반복 작업은 전용 도구와 컨텍스트를 가진 서브에이전트(`.claude/agents/*.md`)로 분리합니다.

#### Play 3-3: 단일 진실 공급원 (Single Source of Truth) 원칙

기존 시스템(Jira, ServiceNow, Figma 등)과 마크다운 아티팩트의 공존 전략:

1. **레포 중심**: 마크다운 파일이 원본이며, 외부 시스템은 Git 커밋 링크를 참조.
2. **레거시 중심**: Jira 등이 원본이며, 에이전트가 MCP 커넥터로 시작 시 읽고 종료 시 기록.
3. **상호 연결(최소 요건)**: 마크다운에 티켓 ID 명시, 티켓에 마크다운 커밋 SHA 명시.

#### Play 3-4: `CLAUDE.md` 지식 운영

- 신입 엔지니어가 첫날 필요한 핵심 규칙만 1페이지 이내로 압축 유지.
- 빌드/테스트/린트 명령어, 아키텍처 규칙, 에이전트가 자주 틀리는 실수 기재.
- **2회 규칙**: 에이전트가 같은 실수를 2번 반복하면 즉시 `CLAUDE.md`에 교정 지침을 반영.

#### Play 3-5: Skills와 Hooks의 조합

- **Skills(스킬)**: 사내 지식과 모범 사례를 제공하는 권고형 가이드 (`.claude/skills/`).
- **Hooks(훅)**: 절대로 어기면 안 되는 규칙을 강제하는 결정론적 차단 장치 (생성된 코드 수정 방지, 포맷터 자동 실행, 민감 자격증명 차단).

### Stage 4: Test (검증) — 자체 피드백 루프와 상시 Evals

#### Play 4-1: 에이전트 자체 피드백 루프 (Feedback Loop)

- 에이전트가 사람에게 보고하기 전, 단일 명령어(`make test`, `npm test`)로 자체 검증하도록 구성.
- **버그 수정 TDD 절차**:
  1. 버그를 재현하는 실패 테스트를 먼저 작성하고 커밋.
  2. 테스트 파일 수정을 훅으로 잠근 상태에서 에이전트에게 본 코드를 수정하여 통과하도록 지시.
- **UI 검증**: 브라우저나 스크린샷 MCP 도구를 통해 목업과 시각적으로 대조하며 반복 조정.
- 완료 조건: "테스트가 실패하면 테스트를 지우거나 바꾸지 말고, 구현 코드를 고쳐라."

#### Play 4-2: CI 지속적 평가 (Continuous Evals)

- 모델 업그레이드나 프롬프트, `CLAUDE.md`, 스킬, 훅 설정이 변경될 때 에이전트 작업 능력이 퇴행(Regression)하지 않는지 검증하는 테스트 스위트.
- 실제 과거 작업 20~50개를 선별하여 프롬프트와 정답 판정 스크립트로 구성.
- 설정 변경 PR 발생 시 또는 정기 스케줄로 CI 상에서 비대화형(`claude -p`)으로 실행하고 통과율 미달 시 머지 차단.
- 프로덕션 장애가 발생할 때마다 해당 유형의 회귀 방지용 Eval을 스위트에 필수 추가.

### Stage 5: Deploy (배포) — 양방향 리뷰 및 승인 관문

#### Play 5-1: 양방향 PR 리뷰 루프

- Claude가 인입되는 모든 PR을 `REVIEW.md` 기준(버그/로직 오류, 보안/취약점, 명세 및 설계 준수)으로 다단계 검토하고 심각도 순으로 보고.
- 리뷰 댓글에 `@claude`를 호출하면 에이전트가 피드백을 반영하여 수정 커밋을 직접 푸시.
- 인간 리뷰어는 코드 한 줄 한 줄 검사하는 대신, **원래 의도와 비즈니스 위험**을 판단하는 상위 결정에 집중.
- 리뷰에서 2번 이상 지적된 사항은 `CLAUDE.md`로 역피드백하여 다음 PR부터 원천 차단.

#### Play 5-2: 릴리스 승인 관문 훅 (Approval Gates)

- 프로덕션 배포 등 위험 작업은 사전 승인 토큰이나 릴리스 권한이 없을 경우 훅(`PreToolUse`)에서 즉시 실행 차단(`exit 2`).
- **규제 기업용 엔터프라이즈 관리형 설정 (`managed settings`)**:
  - `permissions.deny`: `.env`, 비밀번호 경로, 임의의 웹 호출(`curl`, `wget`) 차단.
  - `permissions.allow`: 안전한 로컬 빌드, 테스트, 린트 명령어 사전 허용.
  - `sandbox`: OS 레벨 도메인 허용목록 강제, `~/.ssh` 및 클라우드 자격증명 격리.
  - `allowManagedHooksOnly`: 관리자 승인 훅 외에 로컬 훅 임의 추가 차단.
  - `strictKnownMarketplaces`: 검증된 사내 플러그인 마켓플레이스만 허용.

#### Play 5-3: CI/CD 파이프라인 통합

- 실패한 빌드 원인 분석, 플레이키(flaky) 테스트 분류, 변경 로그 초안 작성 등 읽기 전용 판단 단계부터 `claude -p` 적용.
- 린트 교정, 문서 동기화, 리뷰 피드백 반영 등 쓰기 작업은 반드시 PR 브랜치 형태로만 제출(main 직접 푸시 불가).
- 환경별 권한 분리: 개발 환경(자율 배포) → 스테이징(부분 자동) → 프로덕션(릴리스 매니저 승인 필수).
- 롤백(Rollback) 경로를 단일 명령어로 표준화하고 평소에 상시 리허설하여 장애 시 즉각 복구 보장.

---

### Stage 6: Maintain (유지보수) — 자율 순환 루프 완성

인간이 먼저 호출하지 않아도 모니터링 트리거가 에이전트를 가동하고, 결과물이 다시 `intent.md`로 유입되는 닫힌 루프(Closed Loop)를 구축합니다.

#### Play 6-1: 제어 밴드(Control Bands) 기반 자동 대응

- 결정론적 스크립트가 운영 지표(CI 실패율, 배포 후 5xx 에러율, PR 리드타임 등)를 감시 (`bands.yaml`).
  - **1σ(경미한 변동)**: 로그만 기록.
  - **2σ(주의 수준)**: 에이전트를 읽기 전용으로 호출하여 로그 분석 및 원인 진단.
  - **3σ(심각한 이탈)**: 에이전트가 조치 제안(수정 PR 발행 또는 기승인된 롤백 런북 실행).
- 진단 및 수정 제안은 Stage 1 포맷인 `intent.md`로 작성되어 정규 파이프라인으로 재투입.

#### Play 6-2: 상시 코드베이스 보안 스캔 (Claude Security)

- 배포 직전 1회성 진단 탈피. 주간 단위 스케줄로 최신 고성능 모델을 통해 전체 레포지토리 전수 스캔.
- 발견된 취약점 중 단일 수정 가능한 건은 PR 리뷰 관문으로 직행, 구조적 문제는 `intent.md`로 발행해 기획 단계부터 재검토.
- 수정 완료 건은 회귀 Evals에 케이스로 추가하여 동일 취약점 발생 방지.

#### Play 6-3: 온콜 협업 (Claude Tag)

- Slack/Teams 등 장애 대응 채널에 Claude가 전용 계정으로 상주하여 1차 대응(First Responder) 역할 수행.
- 엔지니어들과 스레드에서 실시간으로 원인 가설 검증, MCP 연동을 통한 정상화 확인, 포스트모템(사후 보고서) 초안 작성.
- 채널의 대화 내역 자체가 감사 추적 기록이 됨.

## 3. 전체 라이프사이클 아티팩트 체계 맵

| 단계                       | 입력 아티팩트             | 에이전트 작업                     | 산출/트리거 아티팩트           | 인간의 핵심 책임                      |
| :------------------------- | :------------------------ | :-------------------------------- | :----------------------------- | :------------------------------------ |
| **1. Plan (기획)**         | 비즈니스 요구 / 장애 알림 | 인터뷰 진행 및 요구 명확화        | `intent.md`                    | 문제 정의 타당성 검토 및 승인         |
| **2. Design (설계)**       | `intent.md` + 사내 Skills | 정책 반영 명세 및 화면 목업 도출  | `spec.md`                      | 정책 충돌 조율 및 최종 설계 승인      |
| **3. Build (구현)**        | `spec.md` + `CLAUDE.md`   | 계획 수립(Plan mode) 후 코드 구현 | `plan.md` + 코드 Diff          | 작업 분할 타당성 검토, 예외 승인      |
| **4. Test (검증)**         | 코드 Diff                 | 자가 검증(TDD) 및 CI 평가         | 테스트 결과 로그, CI Eval 결과 | 완료 판정 검증, 신규 회귀 케이스 추가 |
| **5. Deploy (배포)**       | PR 브랜치                 | 양방향 코드 리뷰 및 CI 분석       | 리뷰 결과, 릴리스 PR           | 비즈니스 위험 평가, 프로덕션 승인     |
| **6. Maintain (유지보수)** | 모니터링 메트릭 이탈 알림 | 원인 진단 및 긴급 조치/롤백 제안  | 진단 리포트, 신규 `intent.md`  | 이상 징후 트리아지, 임계치 튜닝       |
